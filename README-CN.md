# QCP

[English](README.md) · 简体中文

QCP 是面向低延迟应用的 UDP 传输协议，同时适用于客户端到服务端和服务端到服务端。[Go 库](https://github.com/neko233-com/qcp-lib-go)是参考实现。

## 适用场景

| 拓扑 | 常见用途 | 交付要求 |
| --- | --- | --- |
| **客户端 → 服务端** | 玩家操作、位置快照、实时遥测 | 对能被后续更新覆盖的状态，优先交付最新值。 |
| **服务端 ↔ 服务端** | 游戏网关回源、跨地域游戏 RPC、实时事件流、状态复制 | RPC 和业务事件采用可靠有序交付。对允许新值覆盖旧值的快照，使用最新状态交付，避免重传过期状态。 |

当两端都由团队控制、可以开通 UDP，并能按消息类型选择交付语义时，QCP 很适合服务间通信。稳定内网建议先以 WebSocket/TCP 为基准。弱网对比应统一负载大小、交付语义和并发量，同时观察可靠 RPC 的 P99、超时率和送达率。业务重试仍需请求 ID 和幂等处理。

### 交付语义

| 模式 | 预期行为 |
| --- | --- |
| **REALTIME** | 优先交付较新的状态，允许跳过迟到或丢失的旧更新。单次更新应小于 UDP 数据报载荷上限。 |
| **CRITICAL** | 协议设计支持按截止时间恢复。使用前确认对应语言绑定实现了截止时间语义。 |
| **BATCH** | 可靠有序，用于必须按顺序处理的指令和业务事件。 |

Go 原始传输接口提供 `Dial`、`Listen`、`Send` 和 `RecvWait`。超过 MTU 的可靠载荷会分成有序数据块。需要保留消息边界时，使用长度前缀或已有的消息帧协议。

Go 服务之间可以通过 `qcp.ListenStream` 和 `qcp.DialStreamContext` 获得 `net.Listener` 和 `net.Conn`，在有序流上叠加 TLS，再复用现有 RPC 或消息帧。服务间身份认证可由两端校验证书完成。

## 网络与部署

- QCP 要求两端运行环境支持 UDP，且链路允许 UDP。Go 等原生运行时可直接创建 UDP socket。标准浏览器 JavaScript 和浏览器内的 Unity WebGL 无法创建原始 UDP socket。Unity 包包含试验性的微信小游戏 UDP 桥接，接收路径仍待实现。浏览器端需使用平台提供的应用层传输。
- 服务间链路优先放在私网或认证隧道里。敏感流量应在有序字节流上使用 TLS，或使用其他经过认证的加密层。启用证书校验，并限制 UDP 监听端的来源。
- 部署时配置 UDP 转发，监控丢包、重传、超时和重连。为 UDP 受限或尾延迟退化的环境保留 WebSocket/TCP 切换配置。
- 单条可靠有序流依然可能等待丢失的数据包。只有业务允许跳过旧更新时，最新状态交付才能减少这类等待。

## 延迟对比

以下数值来自**模拟模型**，用于比较不同假设下的交付延迟。选型时请以相同负载和交付要求进行真实 socket 实测。[完整报告与测试方法](https://github.com/neko233-com/qcp-benchmark/blob/main/%E6%80%A7%E8%83%BD%E5%AF%B9%E6%AF%94%E8%A1%A8%E6%A0%BC.md)。

| 场景 | **`QCP` P50** | **`QCP` P99** | TCP P50 | TCP P99 | KCP P50 | KCP P99 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| LAN | **950 µs** | **999 µs** | 1.583 ms | 1.665 ms | 4.2 ms | 5.294 ms |
| Wi-Fi | **9.505 ms** | **17.001 ms** | 15.842 ms | 50.001 ms | 22.203 ms | 24.216 ms |
| 4G | **23.521 ms** | **31.5 ms** | 39.201 ms | 104.166 ms | 52.206 ms | 65.299 ms |
| 3G | **70.658 ms** | **80.301 ms** | 117.763 ms | 285.495 ms | 152.215 ms | 181.219 ms |
| 拥塞 | **49.445 ms** | **60.2 ms** | 82.408 ms | 202.003 ms | 102.233 ms | 132.26 ms |
